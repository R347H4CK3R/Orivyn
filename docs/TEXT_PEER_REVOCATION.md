# Durable text peer-generation revocation

This is a dormant persistence boundary toward secure foreground sync, not working automatic synchronization. No listener, discovery, certificate provisioning, pairing UI, send permission, transport activation or external connection was added. The native TLS probe remains disabled/control-only. Existing manual imports/exports and conversation behavior remain unchanged.

`revokeTextPeer(peerCertificateSHA256:pairingGeneration:)` commits a persistent rejection tombstone and deletes matching pending/delivered outbox rows and receive receipts in one SQLite IMMEDIATE transaction. Outbox scope uses the remote recipient pin; receive scope uses the remote sender pin. The matching generation is required. Other peers/generations are preserved. Idempotent repeated revocation performs cleanup again without duplicating the tombstone. Already committed conversations are preserved; revocation neither retracts remote data nor undoes a receive that committed first.

Staging, receive (including exact receipt replay), and delivery acknowledgement check the rejection list within their write transaction. An acknowledgement checks through the persisted outbox loader, so deleted/revoked drafts cannot be marked delivered. Draft loading and pending discovery fail when revocation metadata is unavailable. Returned IDs/payloads are data, not live transport leases: already returned in-memory values cannot be recalled. A future native coordinator must cancel/invalidate active connections and callbacks at the same revocation boundary and recheck current scope before every operation.

`isTextPeerRevoked` is a rejection query, **not authentication or consent**. A false result does not establish pairing, certificate identity, user approval, an authorized endpoint or permission to send. A different generation remains a different scope and still requires fresh native pairing/consent. Calling these low-level APIs with pin labels cannot substitute for mutual TLS and protected identity provisioning.

## Migration, damage and bounds

Legacy databases have SQLite `user_version=0` and no revocation tables. One transaction creates the marker and rejection tables and sets `user_version=1`, preserving existing outbox/receipt identities and history. This header sentinel is separate from the tables: loss of either or both tables, a missing marker row or an unknown header version does not silently recreate an empty rejection list. Sync operations fail closed; ordinary local history reading, saving and erasure remain available. Future database migrations must deliberately preserve/update this version gate.

There is no tombstone eviction or expiry. At 10,000 entries a new revocation fails without partial cleanup or a false success; repeated existing revocation remains idempotent. The caller must treat any failed revocation as uncommitted and keep transport paused rather than claiming trust was durably removed. Each entry stores only the 32-byte peer-pin label and generation UUID, not conversation text. History erasure clears transfer payloads but retains this security rejection metadata so erasure cannot revive a revoked generation. Normal backup export excludes it.

The sentinel is not authenticated database integrity or rollback detection. Restoring an older entire database, or coordinated tampering with tables and header, can remove the record of revocation. Installation-bound Keychain recovery and authenticated trust storage remain future work. Cleanup proves logical row removal only: SQLite/WAL pages may retain historical bytes; no physical/forensic purge is claimed. Missing transfer tables do not prevent revocation, while a failure deleting an existing table's scoped rows rolls the whole transaction back.

## Verification

99 portable XCTest cases passed against the exact production persistence/model sources: 11 new revocation cases and 88 existing cases. New tests cover reopen/replay/stage/late acknowledgements; pending and delivered cleanup; scope selectivity/idempotence; history erasure retaining revocation; single/both metadata-table loss; legacy migration preserving existing drafts and receipts; a migration failure rolling back newly created metadata; marker/header damage; 10,000-entry capacity without eviction; trigger-injected outbox/receipt deletion rollback; and two separate SQLite connections racing receive against revocation. The race verifies either an earlier committed receive remains or a later receive is rejected, with no post-revocation retry admitted. It is not a power-loss test.

Eight Python backup-policy/persistence-integrity guards also passed. Independent read-only review found no blocking issue and confirmed the transaction/scope boundaries.

The host used Swift6.1.3, installed SQLite runtime3.46.1 and the already available SQLite3.50.4 header. Their exact hashes and versions are recorded; only common SQLite APIs were exercised. This is Linux host evidence, not Apple's SQLite/runtime, iOS, simulator, device, lock/suspension or two-device verification. `scripts/run_system_sqlite_tests.py` accepts explicit local header/library/toolchain paths and performs no downloads; the original amalgamation-based runner remains supported.
