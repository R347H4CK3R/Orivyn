# Durable selected-text outbox

Private implementation step from caef1e2. This is sender-side SQLite persistence, not an enabled sync service. No UI action, listener, discovery, transmission, pairing, certificate provisioning or native build was added. Existing manual reviewed-text export remains unchanged. There are no calls from the TLS probe or AppModel to these new APIs.

`stageTextSend` accepts the existing immutable ReviewedTextSnapshot (1–100 selected conversations, at most 1,000 completed messages and 5 MB; no attachments or memories). Under one IMMEDIATE transaction it verifies the selected source records still exactly match the reviewed values, then persists those exact reviewed bytes. A changed, deleted, newly streaming or oversized source fails before a draft is written. The payload is never regenerated from later edits. Staging is not live send consent: a future session must freshly review and authorize the stored immutable payload.

Every draft binds a locally generated transfer UUID, separate sender and receiver certificate-pin labels, pairing generation, and receiver erasure epoch. Sender/receiver pins must be distinct 32-byte values. The receiver-side identity intentionally uses the SENDER pin; it is not the outgoing destination pin. These labels do not authenticate either device. Identity provisioning and the actual pinned channel must establish them; peer-provided strings cannot substitute for that evidence.

Restart can list pending IDs and load a bounded immutable draft; it never automatically resumes transmission. Payload reload validates the backup shape, text-only restrictions and canonical bytes, rejecting unknown fields, malformed payloads and noninteger delivery-state corruption. This is structural checking, not authenticated database tamper/rollback detection. If the outbox table is externally lost, reopening creates an empty table; it cannot restore pending transfers. Future recovery must not send stale in-memory drafts absent from durable state.

`recordTextDeliveryReceipt` atomically marks a draft delivered only when the complete identity and exact payload match its persisted draft. The operation is idempotent and survives reopen. It is a low-level persistence API, NOT proof of a remote commit or a network receipt verifier. Only a future authenticated coordinator may call it after verifying the receiver's committed receipt bound to the current scope; a successful socket write alone must never call it. Lost acknowledgements leave the sender pending; retrying the exact draft against the receiver's durable receipt API avoids a second conflict copy. A new transfer UUID for the same content can still create another conflict copy: causal revision reconciliation remains unfinished.

Pending and delivered rows retain exact private text, bounded in total to 50 MB payload bytes and 10,000 rows. SQLite/WAL/metadata add overhead. Capacity rejects new drafts without eviction. `discardTextSend` explicitly removes a draft or completed receipt without deleting source conversations; a late receipt then fails. Individual/all conversation erasure atomically clears ALL outbox rows alongside history and receive receipts, including delivered rows. Failures clearing existing rows roll back erasure; absent outbox metadata does not block erasure. Already returned in-memory values, remote copies and forensic storage erasure are not covered. A future live transport must cancel/invalidate at the same lifecycle/erasure boundary rather than relying on SQLite cleanup alone. Outbox data is excluded from normal backup export.

Verification: 88 portable XCTest cases passed against exact production sources (16 new outbox tests + 72 previous). New cases include exact selected bytes across edit/reopen; stale selection; two synthetic SQLite databases with lost acknowledgement and no duplicate conflict copy; identity/payload substitutions; idempotent delivery receipt; trigger-injected staging/ack/erase failures; explicit discard; individual/all erasure; missing outbox; byte/count capacity; changed streaming/oversized source; malformed/noncanonical payload and delivery-type corruption. Four Python backup-policy guards also pass. No physical devices, network traffic, simulator, Apple SDK, native compilation or power-loss test was used.

Review found no blocking data-loss/scope/erasure issue in this dormant slice. Its storage-type hardening suggestion was applied and tested. Native mutual TLS/Keychain/pairing, explicit send/receive consent, exact manifest/receipt wire protocol, live revocation/foreground coordinator, revision tracking, attachment transactions, and two-device acceptance remain unfinished. No 1.0.0 completion or automatic-sync availability is claimed.
