# Durable reviewed text receive transactions

This is a private implementation step toward foreground device sync, not working automatic synchronization or a release-completion claim. No production UI or transport calls `receiveReviewedText` yet. No network listener, permissions, entitlement, account, dependency, CI dispatch, or external transfer was added.

The production SQLite store now commits a keep-both text merge and a durable receive receipt together in one IMMEDIATE transaction. An exact retry after reopen returns the stored result without creating another conflict copy or overwriting later local edits. A reused transfer UUID with changed exact bytes, certificate-pin label, or pairing generation fails closed. Conflicts preserve local records and copy incoming records. Empty snapshots never delete local content. Manual backup imports retain their previous behavior, including repeated conflict copies.

The receive API accepts at most 5,000,000 bytes, rejects all attachments and memory notes, and rejects streaming messages. Receipt storage retains exact input bytes to avoid inventing a portable cryptographic implementation: at most 50,000,000 payload bytes and 10,000 receipts. There is no eviction that could silently permit replay. Full capacity rejects new receives without writes. These are payload bounds; SQLite pages, metadata, summaries, and WAL add overhead. The stored summary is historical commit evidence, not current local content.

Receipts contain private text. Both individual conversation deletion and erase-all clear all receipt payloads and rotate a database-local receive epoch atomically with deletion. Older receive scopes then fail rather than resurrect deleted data. This deliberately pauses unrelated in-flight receives too; a future coordinator must obtain a fresh reviewed scope. Failed deletion rolls back content, receipts, and epoch. Normal manual exports exclude receipts and epoch. SQLite secure deletion and WAL do not establish forensic secure erasure.

Missing existing epoch rows or receipt tables are not silently regenerated by receive/reopen. A first schema migration creates both transactionally. This is not authenticated database tamper/rollback detection: coordinated loss of both tables or restoration of an old database needs an installation-bound recovery policy. A database copy also copies its receive epoch; no installation or peer identity is derived from this UUID.

`ReviewedTextReceiveIdentity` is only a local transaction scope. Its 32-byte certificate pin label does NOT prove authentication, and naming the API “reviewed” does not enforce review. The native coordinator must establish mutual TLS, validate the pin, bind the current native connection/nonces/pair generation/receiver epoch/exact immutable payload, enforce foreground/unlocked state and revocation, and collect explicit consent before invoking it. Never wire an untrusted network message directly to this method. The existing security design remains required.

Remaining gates: authenticated identity and Keychain/SecIdentity integration; physical pairing; exact-payload review UI; live consent/revocation coordinator; durable sender/outbox state and revision reconciliation; installation binding and explicit recovery; attachment file/DB commit protocol; native compilation; suspension/lock, true crash/power-loss and two-iPhone acceptance. A new transfer ID for the same conflicting content can still create another copy: causal revision synchronization is not implemented by these receipts. Memory and attachment transfer remain unsupported. No automatic deletion propagation is provided.

Portable verification: 53 XCTest cases passed on Linux Swift 6.1.3 against the exact modified production SQLite and model sources, with the host SQLite shared library. Thirteen new behavioral tests cover reopen retry, changed scope/payload, receipt/content failure rollback, failed erase rollback, individual/all erase epoch rotation, unsupported content, two-connection concurrency, missing metadata, bounded receipt capacity, and unchanged manual imports. Forty existing persistence/model/search tests also pass. These are synthetic fixtures, not a native build or device test. The initial harness attempt lacked the test-target SQLite module include path and failed compilation; the corrected documented command passed.

Review follow-up: missing receipt tables previously blocked existing individual/all history erasure. Erasure now checks table presence inside its transaction and skips absent metadata only; it never recreates it, and new/stale receives both remain blocked. Errors clearing existing receipts still roll back so private receipt text is not left behind. Initialization explicitly closes SQLite handles on every failure. Final regression: 56 portable tests passed (16 receive tests + 40 existing), including missing-receipt erasure, missing-epoch-row erasure, and a Linux-only descriptor check across 20 failed migrations.
